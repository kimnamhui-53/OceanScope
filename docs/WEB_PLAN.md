# 오션스코프 해양환경 뷰어 (web/) — 설계와 구현 메모

보고서 자동생성과 **별개 산출물**. 같은 분석 코드를 쓰되 출력만 다르게 한다.

| | 보고서 파이프라인 | 웹 뷰어 |
|---|---|---|
| 목적 | 발간용 HWPX | 화면에서 바로 보기 |
| 입력 | 연도(1~12월 15일 고정) | 사용자가 고른 날짜·영역·항목 |
| 출력 | cartopy PNG (dpi 800) | 같은 cartopy PNG (dpi 100/300) |
| 장식 | 로고·울릉독도 박스·관측점 포함 | 제거 (지명 라벨만 유지) |
| LLM | 월별 코멘트 작성에 사용 | 사용 안 함 |

## 1. 구조

```
브라우저 (index.html + app.js, 빌드 도구 없음)
   │  POST /api/render {date, bbox, layers, quality, id, pw}
   ▼
FastAPI (web/server/app.py)
   │
   ├─ jobs.py      워커 스레드 1개로 직렬 처리 + 진행률
   ├─ pipeline.py  자료 확보 → 레이어별 render() → 캐시
   │    ├─ code/download_data.py   원본 nc 다운로드 (계정 선택)
   │    └─ code/{eddy_tracking,eastsea_current,eastsea_sst}.render()
   │
   └─ web/cache/<날짜>/<레이어>_<설정해시>.png  +  .json
```

**Leaflet 같은 웹 지도를 쓰지 않는다.** 기존 cartopy 코드가 이미 필요한 그림을
그리고 있으므로 그대로 재사용하고, 웹은 입력 폼·실행·미리보기·다운로드만 맡는다.
덕분에 분석 결과가 보고서와 100% 같은 코드에서 나온다.

### 왜 워커 스레드 1개인가
matplotlib 은 스레드 안전하지 않고 소용돌이 탐지는 CPU 를 통째로 쓴다.
동시에 여러 건을 돌리면 오히려 전부 느려지므로 큐에 넣어 한 건씩 처리한다.

## 2. 코드 재구성 (Phase 0)

세 스크립트가 지도 만드는 40여 줄을 글자 하나 안 틀리고 복사해 쓰고 있었다.
공통부를 `code/mapstyle.py` 로 빼고, 각 스크립트를 `render()` 함수로 바꿨다.

```
code/mapstyle.py          지도 축·육지·해안선·격자선·지명·관측점·박스·로고
    DOMAIN                동해 기본 분석 도메인 (126–142E, 34–50N)
    DEFAULT_EXTENT        기본 표출 범위
    is_eastsea_view / analysis_domain / auto_figsize   표출 범위 → 분석 범위·그림 크기
    CENTRAL_LON           투영 중심 경도 (고정 — 3절 참고)
    REPORT_STYLE          로고·관측점·박스 포함, dpi 800
    WEB_STYLE             장식 제거, dpi 100
    make_map / decorate / save / warmup

code/eddy_tracking.py     load() / mask_domain() / detect() / build_stats() / render()
code/eastsea_current.py   load() / arrow_skip() / view_slices() / build_stats() / render()
code/eastsea_sst.py       load() / build_stats() / render()
```

각 파일에 `if __name__ == '__main__': render(sys.argv[1], style=REPORT_STYLE)` 을
남겨 두어 `run_pipeline.py` 의 subprocess 호출이 그대로 동작한다.

### 원본에서 발견해 바로잡은 것 — 냉수성이 마스킹 전 자료로 탐지되던 문제

원본 `eddy_tracking.py` 는 이 순서였다.

```python
hhh1 = sla * 100        # ← 냉수성 탐지에 쓰는 배열을 여기서 만들고
for i in range(50):
    sla[i, i+79:130] = np.nan    # ← 마스킹은 그 다음
...
hhh1 = sla * 100        # ← 난수성은 마스킹된 자료로 다시 만든다
```

즉 **냉수성은 마스킹 안 된 자료, 난수성은 마스킹된 자료**로 찾고 있었다.
그 결과 냉수성 쪽에 동해 밖(도메인 동쪽 끝 등)의 소용돌이가 몇 개 섞인다.
2024-01-15 기준 141.06°E / 36.43°N 의 1개가 그렇다.

**2026-09-07 에 바로잡았다.** 지금은 난수성·냉수성 모두 마스킹된 자료로 탐지한다.

자료가 있는 17개 날짜로 확인한 영향:

| 값 | 변화 |
|---|---|
| 난수성 (`warm`) | **전부 그대로** |
| 울릉 난수성 (`ulleung_warm`) | **전부 그대로** |
| 독도 냉수성 (`dokdo_cold`) | **전부 그대로** |
| 동해 전체 냉수성 (`cold`) | 날짜당 0~3개 감소 (14일치 합계 −19) |

즉 표 1의 울릉·독도 값은 영향이 없고, 동해 전체 냉수성만 줄어든다. 줄어든 것은
전부 동해 밖 오탐지다. 발간된 2025년판 보고서의 '동해 전체 냉수성' 수치와는
달라지므로, 과거 수치를 대조할 일이 있으면
`output/eddy_tracking/json_baseline_legacy/` 에 구 동작 결과를 남겨 뒀다.

웹 캐시는 `pipeline.ALGO_VERSION` 이 캐시 키에 들어가므로, 앞으로 분석 코드를
바꿔 결과가 달라질 때 이 값을 올리면 옛 그림이 그대로 나오지 않는다.

## 3. 성능 (Phase 0)

측정해 보니 병목은 한 곳이었다. 냉수성 1회 탐지 123.7초 중:

| 구간 | 시간 | 비중 |
|---|---|---|
| `polygon.contains` 격자 이중 for | 115.5초 | **93.4%** |
| 등고선 생성 | 5.0초 | 4.0% |
| 최대 지름 `geod.inv` O(n²) | 3.0초 | 2.4% |

고친 것:

| 문제 | 방법 | 효과 |
|---|---|---|
| 격자마다 `polygon.contains(Point)` 파이썬 이중 for | `shapely.contains_xy()` 벡터화 (판정 기준이 동일해 결과 불변) | 탐지 250초 → **4~5초** |
| 레벨마다 figure 생성 (1000회) | 축 하나 재사용 후 등고선만 제거 | 5초 → 1초 |
| extent 마다 `Mercator(central_longitude=...)` 를 새로 만듦 | `CENTRAL_LON` 고정 — Mercator 에서 중심경도는 x 평행이동일 뿐이라 그림은 같다 | 영역 바꿀 때 재투영 10초 제거 |
| 화면 밖 화살표까지 렌더 | `view_slices()` 로 표출 범위만 quiver | 줌 렌더 19초 → 0.4초 |
| 전 지구 격자선 생성 | 표출 범위 ±1칸만 | 좁은 영역에서 이득 |
| 프로세스 첫 육지 렌더 11초 | `mapstyle.warmup()` 을 서버 기동 시 호출 | 첫 요청 지연 제거 |

O(n²) `geod.inv` 는 계획서에서 주요 병목으로 봤지만 실제로는 2.4%라 손대지 않았다.

**회귀 검증**: 위 성능 수정만 넣은 시점(마스킹 정정 **전**)에 기준선 14일치
(2024년 12개월 + 20250115 + 20260818)와 대조해, 소용돌이 개수 4종은 물론
**각 소용돌이의 중심좌표·반경·진폭까지 전부 일치**함을 확인했다. 수온 통계
14일치도 전부 일치, 보고서 해류도는 md5 까지 동일했다.
즉 성능 수정은 결과를 바꾸지 않았고, 그 뒤 숫자가 달라진 것은 2절의 마스킹
정정 때문이다(냉수성만). 전체 검증이 67초에 끝난다(이전엔 하루당 4분 이상).

기준선 폴더는 마스킹 정정 시점에 한 번 교체했다.
`json_baseline/` = 현재 동작, `json_baseline_legacy/` = 정정 전(발간 보고서) 동작.

## 4. 영역(위·경도) 처리

분석 범위는 `mapstyle.analysis_domain(extent)` 이 표출 범위로부터 정한다.

| 요청한 표출 범위 | 자료 슬라이스 · 소용돌이 탐지 | 동해 경계 마스킹 |
|---|---|---|
| 동해 기본 범위(`DEFAULT_EXTENT`) 안 | **고정 도메인 126–142E / 34–50N** | 적용 |
| 그보다 넓은 영역 | **요청 영역 + `ANALYSIS_MARGIN`(1.25°)** | 없음 |

그림 표출(`ax.set_extent`)과 `stats['view']` 통계는 어느 쪽이든 사용자 영역이다.
`stats['warm']`/`['cold']` 는 분석 범위 전체 개수이고 `stats['scope']` 가
그게 '동해'인지 '분석영역'인지 알려 준다.

**초기 버전은 언제나 고정 도메인만 분석했다.** `mask_domain()` 이 배열 인덱스
(`sla[i, i+79:130]`, `sla[:, 125:130]` …)로 쓰여 있어서 도메인을 바꿀 수 없었기
때문이다. 지금은 같은 마스킹을 위경도 식으로 다시 썼다.

```
lat <= 34.5 · lon <= 126.5 · lon >= 141.5          도메인 가장자리 (EDGE_TRIM)
lat <  40.125 이면서 (lon - lat) >= 101.875        동해 경계 대각선
```

0.125° 격자에서 옛 인덱스식과 **NaN 위치가 완전히 같음을 실측 확인**했고,
격자 간격이 달라져도 그대로 성립한다. 동해보다 넓은 영역을 요청하면 대각선은
빠지고 분석창 네 변의 `EDGE_TRIM`(0.5°)만 남는다 — 요청한 영역이 전부 분석된다.

소용돌이 탐지는 격자 수에 민감하다(등고선 500단계 × 후보마다 격자 전체 판정).
실측: 동해 기본 270 deg² 11초 · 540 deg² 15초 · 1,500 deg² 146초. 그래서
`app.py` 의 `MAX_EDDY_AREA = 1000` deg² 에서 끊는다(수온·해류는 제한 없음).

화면에도 "선택한 영역 전체를 분석합니다"라고 적었다.

영역을 좁힐 때 따라붙는 처리:
- figure 크기를 표출 범위 종횡비에 맞춘다 (`auto_figsize`) — 가로로 넓은 영역에서
  지도가 납작한 띠로 눌리며 제목·컬러바와 겹치는 것을 막는다
- 화면 밖 지명 라벨은 그리지 않는다 (`add_places` 가 extent 로 거른다)
- 자료 출처 문구는 축 좌상단 고정 (좁혀도 안 잘린다)
- 화살표 간격 `arrow_skip()` 을 폭에 비례 (기본 범위에서 원본과 같은 2)
- 수온 색 범위를 표출 영역 값으로 (기본 범위에서는 자동 스케일과 동일)
- 격자선 간격도 폭에 맞춰 조정 (기본 범위에서 원본과 같은 4°/2°)

위 여섯 가지 모두 **기본 표출 범위에서는 원본과 같은 값**이 나오도록 맞췄다.

## 5. CMEMS 계정 처리

`copernicusmarine` 2.4.1 은 `get()` 에 `username=`, `password=` 를 직접 받는다.
`download_data.py` 에 `creds` 인자를 더해 그 자리에서만 쓰도록 했다.

- 계정은 요청 본문으로만 받고 작업이 끝나면 `jobs.py` 가 메모리에서 지운다
- 디스크 기록 없음, 로그 출력 없음 (실제로 확인함)
- 브라우저 `localStorage` 저장 안 함
- **비워 두면** 이 PC 에 저장된 로그인(`copernicusmarine login`)을 쓴다.
  저장된 것도 없으면 계정을 입력하라고 안내한다
- 인증 실패는 `download_data.AuthError` 로 구분해 "CMEMS 계정을 확인하세요"라고 표시
- 서버는 반드시 `127.0.0.1` 바인딩

### 원본 파일은 data/ 에 받는다
계획 단계에서는 `subset()` 으로 영역만 잘라 `web/cache/` 에 받으려 했으나,
잘라 받은 파일이 `data/` 에 섞이면 요청 영역을 벗어나는 순간 자료가 비게 된다. 그래서 **보고서와 같은 `get()` 원본 파일**을 같은
`data/<PRODUCT>/<연도>/` 에 받는다. 두 경로가 자료를 공유하므로 중복 다운로드가 없다.
대신 파일이 커서(SLA 35MB + SST 16MB) 새 날짜는 다운로드에 1분 남짓 걸린다.

## 6. 실측 성능

| 요청 | 시간 |
|---|---|
| 캐시 적중 (같은 날짜·영역·해상도) | 0.1 ~ 0.3초 |
| 보유 날짜 · 3항목 · 미리보기(100dpi) | 약 13초 |
| 보유 날짜 · 3항목 · 고화질(300dpi) | 약 11초 |
| 보유 날짜 · 수온만 | 약 1.3초 |
| **새 날짜** · 3항목 (다운로드 포함) | 약 99초 (다운로드 85초 + 렌더 14초) |
| 잘못된 계정 → 오류 안내 | 3초 |

이미지 크기: 미리보기 130~360KB, 고화질 0.9~1.6MB.
